## What it does
Sign in, enter a patient's vital signs, and get one of four urgency levels (**Non-Urgent, Semi-Urgent, Urgent, Resuscitation**) with a recommended action, target wait time, probability breakdown and the factors behind the decision.

**Highlights**
- 🔐 **Sign in with Google, mobile number (SMS one-time code) or as a guest** — every user sees only their own history
- 🎨 **Light, professional theme** — split welcome screen: brand panel on the left third, sign-in on the right
- 🚪 App-style welcome screen, five-tab UI (Assess · Analytics · History · API · About), mobile-friendly
- ⚡ **28 ready-made example patients** (critical → minor) plus a 🎲 random-patient button — each one checked against the model
- 📄 **Professional 5-column footer** — Product · Developers · Legal · Contact. Product links switch sections, Legal links open Features / Privacy Policy / Terms of Use / Medical Disclaimer as pop-ups, and GitHub / LinkedIn / email / API docs are real links
- 💬 **In-app feedback form** (rating + message, optional reply email) stored in the database for the author to read (plain-language templates — have them reviewed before real-world use)
- 🛡️ **Clinical safety net** — red-flag rules (e.g. SpO₂ < 85 %, unresponsive) can *raise* the AI result, never lower it, and the UI shows why
- 🔍 **"Why this result?"** — a what-if explanation per patient: each value is swapped for a normal one and the change in the model's confidence is shown (red raises the level, green lowers it). Plus shock index, MAP, pulse pressure and fever/hypoxia/tachycardia flags
- 📊 Built-in model analytics (KPIs, per-class report, confusion matrix, feature importance, class distribution)
- 🗂️ Anonymous assessment history (no patient names/IDs), deletable anytime — plus "delete my account". **SQLite out of the box, PostgreSQL for production** (just set `DATABASE_URL`)
- 🔒 JWT sessions, hashed single-use OTPs with attempt + rate limits, CSRF-protected OAuth, locked-down CORS, security headers, no internal errors leaked
- 🧪 126 automated tests; train/serve feature code is shared to prevent skew
- 📓 EDA notebook (`notebooks/01_EDA.ipynb`)

## Quick start
> Updating from an older copy? Extract the full zip over your folder (choose *Replace*), then run `check_install.bat` — it lists anything missing or out of date.

```bash
git clone https://github.com/<you>/triavia.git && cd triavia
python -m venv venv && venv\Scripts\activate      # macOS/Linux: source venv/bin/activate
pip install -r requirements.txt
start.bat            # macOS/Linux: ./start.sh
```
App → http://localhost:8501 · API docs → http://localhost:8000/docs

On the first screen choose **Continue as guest**, or try **mobile sign-in**: enter a number such as `+91 98765 43210` — in local demo mode the 6-digit code is shown on screen (no SMS is sent). Google sign-in appears once you add credentials (below).

### Or run with Docker
```bash
docker compose up --build        # app → http://localhost:8501 · API → http://localhost:8000/docs
```
The API image trains the model at build time, runs as a non-root user, and has health checks. Data lives in a named volume (`triavia-db`). Pass your own secrets via `.env` (see `.env.example`).

## Sign-in options

| Method | Works out of the box? | To make it real |
|---|---|---|
| 👤 Guest | ✅ yes (accounts auto-delete after 24 h) | set `ALLOW_GUEST=false` to disable |
| 📱 Mobile (SMS code) | ✅ demo mode: code shown on screen locally / printed in API logs | set `SMS_PROVIDER=twilio` + `TWILIO_*` variables |
| 🔵 Google | needs your own OAuth credentials | steps below |

### Enable Google sign-in
1. [Google Cloud Console](https://console.cloud.google.com/) → *APIs & Services* → *OAuth consent screen* (External, add your email as a test user).
2. *Credentials* → *Create credentials* → *OAuth client ID* → **Web application**.
3. **Authorised redirect URI:** `http://localhost:8000/api/v1/auth/google/callback` (local) and `https://<your-render-app>.onrender.com/api/v1/auth/google/callback` (production).
4. Put the client ID/secret in `.env` (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) or the Render dashboard, and set `FRONTEND_URL` / `BACKEND_PUBLIC_URL` to your real URLs. Restart the API — the Google button appears automatically.

### Enable real SMS (Twilio)
Create a Twilio account, buy/verify a number, then set `SMS_PROVIDER=twilio`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`. Never enable `OTP_DEV_ECHO` in production — it returns the code in the API response.

**How it works:** Google → authorization-code flow with signed `state` + cookie nonce; the API swaps the code for the user's verified profile, then redirects back with a *single-use, 2-minute* code that the frontend exchanges for a session token (tokens never appear in URLs). SMS codes are 6 digits, stored as HMAC hashes, expire in 5 minutes, allow 5 attempts, and are limited to 5 requests/hour per number.

## How the explanation works
For each of the 11 inputs the API re-scores the patient with **only that value replaced by a normal baseline** (e.g. SpO₂ 98 %, heart rate 80) and reports `P(actual) − P(normalised)` for the level the model favoured. It needs no extra libraries (unlike SHAP), is one batched model call (milliseconds), and reads in plain language: *"Oxygen saturation 87 % raised the Resuscitation probability by 5 points."* It explains the **model's** reasoning; safety-net escalations are listed separately. Because the training data is synthetic, the drivers reflect that data, not clinical truth.

## Model performance
Measured on a held-out 20 % test split of the 6,000-sample synthetic dataset (`python model/train.py` reproduces it; values vary slightly by library version):

| Metric | Score |
|---|---|
| Accuracy | ≈ 0.93 |
| Weighted F1 / Macro F1 | ≈ 0.93 / 0.94 |
| ROC-AUC (OvR) | ≈ 0.99 |
| 5-fold CV weighted F1 | ≈ 0.93 ± 0.01 |

These describe the **synthetic** data (which includes ~3 % deliberately missing values, imputed by the pipeline) — **not real-world clinical performance**. Swap in MIMIC / eICU-derived data for genuine evaluation.

## Database: SQLite or PostgreSQL
| | SQLite (default) | PostgreSQL |
|---|---|---|
| Setup | none | set `DATABASE_URL=postgresql://user:pass@host:5432/dbname` |
| Best for | local use, demos | production / hosts with ephemeral disks (Render free tier) |
| Survives redeploys | only with a persistent disk | ✅ |

Tables are created automatically on first start; the same code and the same tests run on both. Run Postgres locally with `docker compose -f docker-compose.yml -f docker-compose.postgres.yml up --build`. Managed options: Render Postgres, Neon, Supabase, AWS RDS — check each provider's current plan limits. Connections are opened per request (simple and fine for demo-scale traffic); add a pool (e.g. `psycopg_pool`) if you expect heavy load.

## Continuous integration
`.github/workflows/ci.yml` runs on every push/PR: installs dependencies on Python 3.11 and 3.12, trains a quick model, runs the full test suite on SQLite **and again on a real PostgreSQL service**, then builds both Docker images and smoke-tests the API container.

## Deployment
**Backend → Render:** *New → Blueprint* (reads `render.yaml`). Set `CORS_ORIGINS`, `FRONTEND_URL`, `BACKEND_PUBLIC_URL`; add Google/Twilio variables if used. `SECRET_KEY` is generated automatically.
**Frontend → Streamlit Cloud:** main file `frontend/app.py`; secrets: `BACKEND_URL = "https://<your-render-app>.onrender.com"`.

## Security notes
- Set a strong `SECRET_KEY` and a specific `CORS_ORIGINS` in production; keep `OTP_DEV_ECHO=false`.
- Rate limiting is in-memory per process; use Redis / a gateway if you scale out.
- Model files are pickles generated locally by `train.py` — never load pickles from untrusted sources.
- SQLite on Render's free tier is ephemeral (users and history reset on redeploy) — set `DATABASE_URL` to a PostgreSQL database to keep them.
- Sessions live in the Streamlit session: a browser refresh signs you out (a deliberate trade-off — no tokens in cookies/URLs).
- Do not enter real patient data.

## Technical decisions
| Decision | Rationale |
|---|---|
| Random Forest | Well-calibrated probabilities, robust on tabular data, easy to explain |
| Balanced class weights | Critical cases are rare |
| MinMax scaling + imputers | Vitals have known bounds; real data has gaps |
| One-hot categoricals | No false ordering between complaints |
| Shared `features.py` | Same code in training and serving → no skew |
| Safety-net rules | ML can miss rare extremes; rules only escalate |
| Backend-enforced auth | The UI login is convenience; the API itself rejects unauthenticated calls |
| Stdlib `sqlite3` | Zero extra dependencies, parameterised queries |
